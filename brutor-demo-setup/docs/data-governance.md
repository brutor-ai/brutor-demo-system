# Data Governance Statement (Art 10)

**System:** Brutor Demo System (consumer loan pre-screening agent)
**Provider and deployer:** Borealis Consumer Finance AB (fictional)
**Classification:** High-risk, Annex III 5(b)
**Version:** 1.0, 2026-09-23
**Owner:** Data Governance, with the Data Protection Officer

> Demonstration document. Every record the system processes is generated by
> the demo's own mock origination system and mock bureau. No real person's
> data is used at any point, and the statement says so wherever a real
> deployment would describe production data.

## 1. Data the system uses

| Data | Source | Purpose | Personal data |
|---|---|---|---|
| Application record: name, date of birth, country, email, employment status, income, expenses, existing debt, amount, term, purpose text | Loan origination system (`brutor-demo-applications-mcp`) | Intake, affordability, classification, letter | Yes (synthetic) |
| Identity verification result: verified flag, match score | Credit bureau (`brutor-demo-credit-bureau-mcp`) | Rule: unverified forces refer | Yes (synthetic) |
| Credit report: score, open lines, total debt, delinquencies, inquiries | Credit bureau | Classification, fraud velocity heuristics | Yes (synthetic) |
| Fraud verdict: clear / review / hit, reasons | Fraud screener (A2A) | Rule: hit forces decline, review forces refer | Derived |
| Affordability result: installment, DTI, disposable income, class | Affordability skill (deterministic) | Rule: unaffordable forces decline | Derived |
| Model outputs: risk band, key factors, recommendation, rationale, letter | Classifier and drafter models through the gateway | Recommendation | Derived; the letter carries the name |

## 2. How the data is generated (demo)

The origination mock creates one to three applications every ten minutes from
a seeded generator. Names are composed from two word lists and are never taken
from a real-person dataset. About 8 percent of applications are above 25,000
EUR, about 5 percent carry a name from the fraud screener's synthetic sanctions
list, and about 3 percent contain a prompt-injection attempt in the purpose
text. The bureau mock derives its answers from a hash of the applicant id so
repeated calls agree. In a real deployment this section would describe the
production sources, their contracts and their update cadence.

## 3. Data quality

- The affordability skill validates every numeric input and reports an error
  as data rather than guessing; an error never becomes an approval.
- The bureau verification score below threshold forces `refer`, so a thin or
  inconsistent identity record cannot be approved automatically.
- The classifier and drafter are asked for JSON with a fixed schema; a
  malformed answer errors the run rather than being interpreted.
- Bureau reads through the gateway are read-only (`readOnlyHint`) and are
  sealed as evidence because the system is flagged `sensitive_data`, so a
  reviewer can prove which report a decision saw.

## 4. Data minimisation and flows

- The models receive only the fields the prompt needs. The email address is
  never sent to a model.
- The fraud screener receives the applicant's name, date of birth, country,
  purpose, amount and three bureau counters; nothing else.
- The gateway records action metadata and, for governed calls, sealed
  digests; request and response bodies are retained under the tenant's
  retention policy, with the EU high-risk floor of 183 days applied once the
  framework is enabled.
- The letter necessarily carries the applicant's name. PII detection is
  therefore switched off on the output surface; the justification is
  recorded in the guardrail configuration description and in this statement.

## 5. Bias review

The system is examined for indirect discrimination each quarter:

1. Outcome distribution (approve / refer / decline) by applicant country and
   by affordability class, compared with the deterministic rules alone.
2. Share of `refer` outcomes attributable to the classifier's `high` band
   versus the hard rules, by country.
3. Manual read of twenty rationales per class for language that references
   protected characteristics.

In the demo the population is synthetic and the review is illustrated in
`evaluation-report.md` section 4. A real review would use production
outcomes and be signed off by the DPO.

## 6. Residency

The bureau MCP server is registered with region `eu-west-1`. The model
providers in the trial are `global`. EU residency enforcement (allowed regions
`eu-west-1`, `eu-central-1`, `block_global`) is available through
`setup.py --residency` and is documented in the README as opt-in, because
turning it on without EU-hosted models refuses every model call. The demo
does not claim that inference runs in the EU.

## 7. Retention and erasure

Application records live in the origination system's data volume for the
lifetime of the demo. Gateway logs follow the tenant retention policy. Erasure
requests would be handled through the platform's data erasure endpoint against
the applicant id; in the demo no request is expected because no person exists.
